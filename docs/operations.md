# 運用ガイド

2-Tap HIIT をリリースしたあとに必要な「お金・アカウント・メンテナンス・リリース手順」をまとめたドキュメントです。
コードの設計は [architecture.md](architecture.md)、仕様は [implementation-brief.md](implementation-brief.md) を参照してください。

## 1. 収益化の方針

| 収益源 | 内容 | 状況 |
| --- | --- | --- |
| 広告（AdMob） | バナー（ホーム・記録・コース選択・セット数選択・完了画面）と、全画面広告（完了後5秒・ホーム⇔記録のタブ切り替え） | 実装済み。本番の広告 ID 待ち |
| 広告を消す（買い切り） | **800円**の買い切り。iOS は App 内課金、Android は Google Play Billing | 未実装（RevenueCat で実装予定） |

- 広告は出し続け、熱心なユーザー向けに「広告を消す」を用意する。両方あると売上が最大になりやすい
- 買い切りにした理由: 「広告を消すだけ」なら、サブスクより買い切りの方がわかりやすく、更新・解約・猶予期間などの管理も不要
- 800円にした理由: 広告を消すのは毎日使うヘビーユーザーで、その人が1年間に生む広告売上（約400〜700円）を下回らないようにするため
- 値段はあとから App Store Connect / Play Console で変えられる。実際のデータを見て調整する

### 課金まわりの決まりごと

- ユーザー ID・ログイン・DB は持たない。購入情報は Apple ID / Google アカウントにひも付いてストア側が保存している
- アプリを消して入れ直しても、機種変更しても、「購入を復元」で戻せる（Apple の審査で必須）
- 買い切りなので解約という概念はない。アカウント機能がないので、Apple が求める「アカウント削除機能」も不要
- 課金の判定は `native/src/features/ads/lib/purchaseClient.ts` の1か所にまとめてある。ここを RevenueCat に差し替え、設定タブに「広告を消す」「購入を復元」を置く

## 2. 売上の試算（目安）

あくまで桁の感覚をつかむための試算です。実際の単価・購入率・継続率は2〜3倍ブレることがあります。

### 前提

| 項目 | 値 |
| --- | --- |
| 広告の売上（毎日使う人1人あたり） | 約1.5円 / 日（バナー約4回 + 全画面約1.25回。日本の単価の目安: バナー 20〜100円 / 1000回、全画面 500〜1500円 / 1000回） |
| 1インストールあたりの平均利用日数 | 約10日（初日でやめる人も、何か月も続く人もいる平均） |
| 1インストールあたりの広告売上 | 約15円 |
| 買い切り（800円）の手取り | 約620円 / 件（消費税・手数料15%を引いた額） |
| 買い切りの購入率 | ダウンロードの1〜2% |

### 広告 + 買い切りの合計（数か月たって落ち着いたころ）

| 月間ダウンロード | 広告 | 買い切り | 月の合計 | 年間の合計 |
| --- | --- | --- | --- | --- |
| 300 | 約4,500円 | 約1,900〜3,700円 | 約6,400〜8,200円 | 約8〜10万円 |
| 1,000 | 約15,000円 | 約6,200〜12,400円 | 約2.1〜2.7万円 | 約25〜33万円 |
| 5,000 | 約75,000円 | 約3.1〜6.2万円 | 約10.6〜13.7万円 | 約130〜165万円 |

広告の売上は「毎日使っている人の数（DAU）× 約45円 / 月」でも見積もれる（DAU 100人 → 約4,500円 / 月）。

### 売上を伸ばすには

- **ダウンロード数**が一番効く: ストアページ（スクショ・説明文・キーワード）を整える（ASO）。「マンションでも静か」「2タップで始められる」を打ち出す。SNS やブログで紹介する
- **継続率**が次に効く: 続けて使う人が増えると、広告も買い切りも伸びる
- リリース後は AdMob と App Store Connect / Play Console の実際の数字で、この試算を見直す

## 3. アカウントと設定の状況

| サービス | 内容 | 状況 |
| --- | --- | --- |
| Apple Developer Program | チーム: **株式会社Pistachio** | 登録済み。最新の規約に同意済み |
| App Store Connect | アプリ「2-Tap HIIT」（ascAppId: `6818840776`）。Bundle ID: `com.yukionishi.twotaphiit` | TestFlight に配信中 |
| Expo / EAS | EAS の projectId は `native/app.json`、ascAppId は `native/eas.json` に記載。証明書・プロビジョニングプロファイル・App Store Connect API キー（APP_MANAGER 権限）は EAS が保管 | 設定済み |
| Google AdMob | **会社用（組織・株式会社Pistachio 名義）のアカウントを新しく作る**。既存の個人アカウントは「個人」から変更できないため使わない | 未作成（Google アカウントの作成待ち） |
| Google Play Console | Android 配信用。開発者登録は25ドル（初回のみ）。AdMob と同じ会社用の Google アカウントで作ると管理が楽 | 未登録 |

### AdMob でやること（会社用アカウント作成後）

1. 会社用の Google アカウントを作る（Gmail で OK。会社か個人かは AdMob 側の設定で決まる）。スマホの Gmail アプリから作ると電話番号の確認が通りやすい
2. AdMob に登録する。アカウントの種類は「組織」、名義は「株式会社Pistachio」、住所は会社の住所
3. 税務情報を登録する: シンガポール（支払い元が Google Asia Pacific のため）、求められたら米国（法人は W-8BEN-E、日米租税条約を適用）。迷ったら税理士に確認する
4. 振込先（会社の口座）を登録する。収益が 8,000円 を超えると支払いが始まる
5. iOS / Android のアプリを登録し、それぞれ「バナー」「インタースティシャル」の広告ユニットを作る
6. 「プライバシーとメッセージ」を設定する: EU 向けの同意メッセージ（GDPR）はオン。ATT の前に出す説明メッセージはオフ推奨（オンにするなら日本語を追加）
7. 発行された ID をアプリに設定する（下の「本番の広告 ID の設定」）

### 本番の広告 ID の設定

| ID | 置き場所 |
| --- | --- |
| アプリ ID（iOS / Android） | `native/app.json` の `react-native-google-mobile-ads` プラグイン設定（いまは Google のサンプル ID） |
| 広告ユニット ID（バナー / インタースティシャル × iOS / Android） | `native/src/features/ads/lib/adUnits.ts` の `PRODUCTION_UNIT_IDS`（いまは空） |

広告ユニット ID が空のあいだは、本番ビルドでも広告は出ない。ID を変えたらネイティブの再ビルド（`pnpm testflight`）が必要。

## 4. リリース手順

### iOS（TestFlight）

```sh
cd native
pnpm testflight            # 本番設定（広告は本番 ID）でビルド → TestFlight へアップロード
pnpm testflight:test-ads   # Google のテスト広告入りでビルド → TestFlight へアップロード（実機での広告確認用）
```

- ビルド番号は自動で +1 される。証明書などは EAS に保管済みなので、2回目以降はほぼ質問なしで進む
- アップロード後、Apple の処理に5〜10分かかる。内部テスターには自動で配られる
- 外部テスター（チーム外の人）に配る場合は、そのビルドを外部テストのグループに追加する。バージョンごとの最初のビルドは Apple のベータ版審査がある
- TestFlight のビルドは90日で期限切れになる。それまでに新しいビルドを上げる

### Android

未対応。Google Play Console に登録したら、EAS Build + EAS Submit で内部テスト配信を設定する。

### App Store に正式に出す前にやること

- アプリアイコンを作る（いまは Expo の初期アイコン）
- プライバシーポリシーの URL を用意する（広告を出すので必須）
- App Store の「App のプライバシー」、Google Play の「データセーフティ」で、広告用のデータ収集を申告する
- EU の「トレーダー情報」を App Store Connect の「ビジネス」画面で申告する（広告収益があるとトレーダー扱いが一般的。住所・電話番号・メールアドレスが EU の App Store に公開される）。公開したくない場合は EU を配信地域から外す
- スクショ・説明文・キーワードを用意する

## 5. メンテナンス

基本はほったらかしで動く。サーバーは不要（アプリ単体で動作。`server/` を使う場合も Cloudflare Workers の無料枠で収まる規模）。
ただし、ストアと SDK の決まりに合わせて **年に1回くらいは手を入れる**。

| 項目 | 内容 | 頻度 | 放置するとどうなるか |
| --- | --- | --- | --- |
| Apple Developer Program | 年会費の更新 | 毎年 | 期限が切れると App Store から消える |
| Android の対象 API レベル | Google Play が毎年求める、新しい Android バージョンへの対応 | 年1回 | 新しい端末の Google Play で検索に出なくなる |
| iOS の SDK | アップデートを出すときは最新の Xcode でビルドする必要がある（EAS が最新環境でビルドする） | 更新するとき | 出さなければ既存のアプリは公開されたまま |
| AdMob の SDK | `react-native-google-mobile-ads` の更新 | 1〜2年に1回 | 古い SDK はいずれ広告が配信されなくなる |
| Expo SDK | 上の2つに追随するために上げる | 年1回 | 新しい OS やストアの要件に対応できなくなる |
| TestFlight | テスト版の期限 | 90日ごと（テスト中のみ） | 期限が切れるとテスト版が起動しなくなる |
| 売上の確認 | AdMob と App Store Connect / Play Console の数字を見て、広告の位置や買い切りの値段を調整する | 月1回くらい | — |

### 年1回のメンテナンスの流れ

1. Expo SDK を最新に上げる（`npx expo install expo@latest` → `npx expo install --fix`）
2. `react-native-google-mobile-ads` など、ネイティブのライブラリを更新する
3. CI（lint・型チェック・テスト・ビルド）が通ることを確認する
4. `pnpm testflight` で TestFlight に上げて実機で確認する
5. App Store / Google Play にアップデートを提出する
